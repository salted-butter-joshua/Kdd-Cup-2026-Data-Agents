## 1. 项目背景

KDD Cup 2026 赛道 **Data Agents for Complex Data Analysis** 要求 Agent 用自然语言问题，在异构数据包（表、库、文档、图/视频）上自主拆题、调工具、交出可核对的表格答案。

这和 ChatBI 不同（口径见仓库根目录 `ChatBI口径.md`）：ChatBI 是在已建好的语义层上「一问一答取数」；本赛道里两张表常常对不齐，Agent 必须自己判断：口径听哪份文档、哪些行对得上才能用、对不上的行直接丢掉。

`task_11`（Easy）：血栓预测库。问重度血栓患者的 ID、性别、诊断。  
标准答案 3 行：`163109 / 2803470 / 4395720`，全是 `F, SLE`。  
口径：`knowledge.md` 规定 `Thrombosis = 2` 才是 severe；性别和诊断在 Patient 表；两表 ID 大量对不上，只保留精确匹配。

## 2. 问题

题目要：列出「重度血栓」患者的 ID、性别、诊断。  
两张表：`Examination`（检查，含血栓级别）、`Patient`（患者花名册，含性别和诊断）。连接两表的钥匙是 `ID`。

### 2.1 当时实际发生了什么

改提示词前，Agent **已经算出正确答案，但没有交卷**。

第 9 步它已经得到两件事：

1. 检查表里「重度」是 `Thrombosis = 2`，一共 **18 条**检查记录。  
2. 这 18 个检查 ID，拿到患者表里去对：只有 **3 个 ID 完全相同**。这 3 个人就是标准答案（`163109`、`2803470`、`4395720`）。

按理说这时就该调用 `answer`，把这 3 行交上去。它没有。

它觉得不合理：医院系统里，检查单上的患者 ID，花名册里怎么会没有？于是开始「修数据」。它发现对不上的检查 ID，花名册里往往有一个**数字很近**的 ID，例如：

| 检查表上的 ID | 患者表里最近的 ID | 差几 |
| --- | --- | --- |
| 163109 | 163109 | 0（本来就是同一个人） |
| 1430760 | 1430761 | 1 |
| 4114610 | 4114606 | 4 |

于是它自己编了一条规则：**差不超过 5，就算同一个人**。后面 7 步全在验证和放大这条规则。16 步用完，始终没调用 `answer`。日志里的失败原因是：步数用尽，没有提交答案。整题跑了大约 163 秒。

如果真按「差 5 以内就合并」去交，会从 3 人扩成大约 18 人，和标准答案对不上。题目和 `knowledge.md` 从来没说过「ID 接近就算同一人」。

**一句话：** 它会过滤、会连表，也已经拿到那 3 个人。失败是因为它把「很多 ID 对不上」当成数据坏了，花剩下的步数去修，最后没交卷。

### 2.2 为什么它会去「修」

**这套题的数据本来就不是完整医院库。** 出题时从大库里抽出两张表，有的行还把 ID 改开了。所以检查表还在、患者表还在，但很多检查 ID 在患者表里找不到。对得上的那一小撮，才是这道题允许使用的人；对不上的 15 条，应直接丢掉，不要猜它们本该对应谁。

Agent 当时没有这条默认策略，再加上四件事把它推去「修」：

1. **提示词只教它怎么说话，没教它怎么收束。** 原来的提示只要求：用 JSON 调工具、最后用 `answer` 交一张表。没有写「ID 必须完全相等才能连表」「对不上就丢掉」「行数少也可以交」。所以它会一直分析到步数用完。  
2. **知识文档里的示例 SQL 本身有错。** `knowledge.md` 说对了：`Thrombosis = 2` 才是重度。但示例查询写成从检查表里选出 `ID, SEX, Diagnosis`。检查表没有性别字段，性别在患者表。Agent 容易照抄这条 SQL，或发现缺列后再想歪招去补。  
3. **它把成百上千个 ID 全部打印出来看。** 工具 `execute_python` 的输出会原样送回给模型。一看见「检查 ID 1430760、患者 ID 1430761」这种挨得很近的数字，就容易联想到「是不是同一人被改了一点」。  
4. **3 行相对 18 行，被当成算错了。** 模型习惯「结果应该覆盖全部重度检查」。看到只剩 3 行，就认为精确匹配有问题，继续挖，直到 16 步用光。

同类题还会再出现：两张表看起来应该能对上，实际只能对上一部分。正确做法永远是：**钥匙必须一模一样才连；对不上的行当这道题里不存在。** 不要发明「数字接近就算同一人」。

## 4. 修改方式

只改 PHASE_1 baseline 提示与步数催交，不改工具、不拆 Agent。

### 4.1 `src/data_agent_baseline/agents/prompt.py`

系统提示增加 Analysis constraints：

- 编码/阈值听 `knowledge.md`，不要扩大词义（severe ≠ most severe，也不是邻近编码的并集）
- 示例 SQL 只当模板，对照真实表改写；知识里提到但本题没有的表直接忽略
- **连表时 ID 必须完全相等**；对不上的行丢掉，不要因为对上的人少就去找「接近的 ID」；禁止用数字差、字符串像不像来硬配，除非题目或知识明确要求这么做
- 实体属性（id / sex / diagnosis）取实体表，事件过滤取事实表
- 探查用 count / distinct / LIMIT，不要打印整列 ID
- 有完整结果表就调用 `answer`，不要因为行数「看起来少」继续挖

任务提示补了一句：先读编码、精确 join、对不上就丢。

观察提示：剩余步数 ≤ 2 时催交 `answer`。

### 4.2 `src/data_agent_baseline/agents/react.py`

组消息时，把剩余步数传给最后一条 observation，用于上述催交。

## 6. 回顾

### 做对的

- 问题定位在「策略」而不是「会不会写 SQL」。  
- 约束写成通用纪律，没有写死本题字段。  
- 最小改动：一层提示词就让 `task_11` 从失败变成与 gold 一致。

### 仍有风险

- 改后仍多了 2 步「确认 18 个 ID 里哪些在 Patient」。有纪律，但还在用 python 打印 ID 列表；层 2 的探查工具才能从根上避免。  
- 只在 `task_11` 上验证过。编码映射、错误示例 SQL、两表 ID 对不齐这三类 Easy 题可能受益；Hard / 视频 / 超长文档仍要层 2、层 3。  
- PHASE_2 的 `prompt.py` 未改。  
- 提示词变长，极端情况下可能挤占上下文；目前 Easy 题可接受。

## 7. 50 题公开集：三次跑分看什么

本地对照 `data/public/output/<task_id>/gold.csv` 打分。规则可以记成三句：

- 看的是**列里的数字/文字**，不看列名叫什么、行怎么排。  
- 少交一行、多数值不对 → 这一列算完全没对上 → 这题往往直接 **0 分**。  
- 答案对了但多交了列 → 扣一点（`0.1 × 多出来的列 / 交的列数`）。**没交表记 0 分**，仍计入平均。

产物在 `artifacts/runs/<run_id>/`：`scores.csv`、`scores_summary.json`，每题还有 `prediction.csv` 和 `trace.json`。

| 轮次 | 平均分 | 交了表 | 满分 | 有预测但仍 0 分 | 超时没交表 |
| --- | ---: | ---: | ---: | ---: | ---: |
| `20260922T012037Z` | 0.724 | 47 | — | — | 3 |
| `20260922T072329Z` | 0.6585 | 45 | 32 | 12 | 5 |
| `20260922T083552Z` | **0.7577** | 46 | 36 | 8 | 4 |

第三轮最高，是因为 `86 / 199 / 200 / 408` 算对了、`379` 从超时变成 0.95。  
**没有修好的是同一批稳定错题，外加 4 道 hard/extreme 一直空跑超时。** 同一套程序连跑，对错会晃，但下面几类错会反复出现。

## 8. 遇到的问题，以及怎么修

下面按「为什么扣分」写。每类先说人话，再举例，最后写修法。修法分三档：

- **提示词**：已经写过一部分（见 `prompt.py` 第 14–20 条），模型仍经常不听。  
- **工具**：让观察里把「你没读全」写得更醒目，少靠模型自觉。  
- **运行**：超时、并发，和会不会算无关。

### 8.1 超时：题还没开始做，600 秒就被杀掉

**人话：** 像考试铃响了，卷子还是白的。不是算错，是根本没交。

**现象：** `task_344 / 396 / 418 / 420`（偶发还有 `379`）没有 `prediction.csv`。`trace.json` 里 `steps` 是空的，失败原因是 `Task timed out after 600 seconds.` 耗时卡在 600.02 秒。都是 hard / extreme。并发 8 路。

**为什么会这样：** 每题在子进程里跑，到点父进程直接 `terminate`。杀掉之后只能写一份空失败包，所以看不到卡在哪。常见可能：第一轮模型调用卡住、Windows 下多进程启动卡住、8 路把接口打满。`379` 有一轮超时、下一轮能交 0.95，说明不完全是「这题一定跑不完」。

**修法：**

1. **超时不要只留白卷。** 子进程定期把已有步骤写到磁盘；杀掉后至少能看到卡在第几步、哪个工具。  
2. **超时题自动重跑 1 次**（单路、不要 8 路一起挤）。这 4 题空跑每题拖平均 0.02，4 题就是 **−0.08**。  
3. 查配置：`run.task_timeout_seconds`、`run.max_workers`。Hard 题可加长超时，或降低并发。  
4. 第一轮 LLM 超过例如 60 秒仍无返回，当作 hang，不要空等到 600。

这是当前**最划算**的分：不改解题逻辑，只要能交表。

### 8.2 把「预览」当成全表（读不全）

**人话：** 只翻了前两页账本就下结论。后面那页还有一笔，没看见。

**典型：`task_22`（Connor Hilton 哪天交的会费）**  
标准答案两个日期：`2019-10-02`、`2019-09-12`。三次里至少两轮只交了第一个。

`read_csv` **不是读全表**。说明书示例是 `max_rows: 20`，模型自己还会填 5 / 10 / 25。工具会读完文件再切前 N 行给你看，同时告诉你真实总行数 `row_count`。这题一共 36 行，第二条会费在第 36 行，预览里没有。观察里已经写了 `row_count: 36`，模型当没看见，直接交卷。

**注意：** 把 `max_rows` 改成 100 治不了根。大表仍然截断；该过滤全表时要用 `execute_python`。

**修法（已落地，细节见第 11.2 节）：** 提示词仍写「预览不能当答案」不够。交 `answer` 时代码检查：若只用过 `read_csv` / `read_json` / `read_doc`、没有成功的 `execute_python`，**拒收**，逼它全表扫描后再交。`read_csv` 观察里补了 `truncated` / `PREVIEW ONLY`。

### 8.3 并列只交一个（漏一行，整列 0 分）

**人话：** 两人并列第一，你只写了一个名字。评委按「这一列内容」对，少一个就算整列不对。

**典型：`task_80`** 资格赛 903、Q3 成绩 `0:01:54` 的车号。标准答案是 `3` 和 `5`，一直只交 `3`。  
打分是列签名的**多重集合**：少一行，整列对不上，这题就是 0，不是「对了一半」。

提示词第 17 条已经写了「极值并列要全交」，模型仍常用「最像的那一条」交差。

**修法：**

1. 提示里再钉死：精确时间/分数匹配用「等于全局条件的全部行」，不要 `ORDER BY … LIMIT 1`。  
2. 交卷前自检：若用 MIN/MAX/精确值筛的，把满足条件的行数打出来，**行数 > 1 必须全交**。  
3. 工具层很难替模型判断「什么叫并列」，但可以在催交观察里重复这一条（剩余步数 ≤ 2 时已经有类似句，仍经常被忽略）。

### 8.4 聚合口径选错（加总、平均、类型）

**人话：** 题问「哪次活动最便宜」，你把一个活动下所有发票加起来比；标准答案比的是**单张发票最便宜**。或者题问「费用类型」，你按菜单明细一行行报。

反复错的题：

| 题 | 它怎么做的 | 标准答案要什么 |
| --- | --- | --- |
| task_25 成本最低的活动 | 按活动把费用 **加总**，三个 Officers meeting 各 20.2 | 单笔费用最低（6 块）的三条 **Speaker** |
| task_163 October Meeting 已批准费用 | 一次交明细，一次交 Advertisement/Food | 按 **type** 汇总一行：`Meeting, 175.39` |
| task_169 2013 SME 月均消费 | 全公司 SUM 再除以 12，得到八千万 | 先人均再 /12，约 **459.96** |

`knowledge.md` 里的公式有时写 Total/12，gold 却是 AVG 后再 /12。只看知识、不看「问的是每个客户还是全体」会偏。提示词第 16、19 条已经在说这件事，这几题还是错。

**修法：**

1. 「最低 / 最高」先算**行级 MIN/MAX**，再算分组 SUM/AVG，两个结果都打出来再选；有知识公式跟知识，不要默认「活动成本 = 把发票加起来」。  
2. 题面出现 type / category，按**类型字段** GROUP BY，不要用备注、描述当分组键。  
3. 「平均」先分清：全体总和 ÷ 12，还是每人平均再 ÷ 12。对一下数量级（459 和 八千万）差太远就要回头。  
4. 仅靠加长提示不够。层 2 更有用：探查工具强制输出「行级极值 vs 分组合计」两张小表。

### 8.5 答案对了，多交了列

**人话：** 题只要学号，你把姓名、班级一起交了。内容没错，照样扣分。

| 题 | 对的部分 | 多余的列 | 分数 |
| --- | --- | --- | --- |
| task_38 客户 3356 现金取款 | `trans_id` 全对 | `date, amount`（有一轮还有 `balance`） | 0.925 → 0.933 |
| task_379 致癌分子第 4 原子元素 | 元素集合对 | 多交了 `count` | 0.95 |

提示词第 14 条专门写了「只交题目要的列」。模型仍爱把调试用的宽表直接交上去。

**修法（已落地，细节见第 11.1 节）：** 不再只警告。真正提交前让模型按题目生成应有列名，与待交列取交集：有交集只留交集，空则原样提交（防列名猜飞）。

### 8.6 样本库对不上日期，就交空表

**人话：** 题问 2013 年 6 月加油站在哪些国家。手里的交易库只有 2012 年 8 月的 1000 行。它很诚实地交了空表。标准答案是 `CZE`、`SVK`（库里能关联到的国家）。

**典型：`task_173`。** 上一轮有人丢掉日期条件、直接交两国，反而满分；这轮按日期滤空了，0 分。

**修法：**

1. 日期滤完是 0 行，先别交空表：看是不是样本库时间范围不对、该用另一张表（例如 `yearmonth.csv`）、或题目要的是「有过交易的加油站国家」。  
2. 空结果要在 trace 里写清：MIN/MAX 日期、行数。若样本明显不含所问月份，改用能关联上的实体表去重。  
3. 这类题有「标准答案迁就样本」的味道，单靠提示不稳，需要做题记录（哪题空结果被判错）。

### 8.7 过滤过宽、取错字段

**人话：** 条件只执行了一半；或者「第二名」取错了哪一列。

| 题 | 错在哪 |
| --- | --- |
| task_180 | 「产品 5、单价 > 29」的人在 2012-08 的消费：交了 153 人还多一列 CustomerID，标准答案 9 个数 |
| task_199 | 第三轮已修好。上轮把「学区均分 > 400」做成「Riverside 县域所有学校」 |
| task_89 | 2008 中国站第二名完赛时间：交 `+14.925`，应为 `+16.445`（名次/圈次列用错） |
| task_200 | 第三轮已修好。上轮把分子里 4 个原子全数了，应为 1 |
| task_408 | 第三轮已修好。上轮用最快圈速算「快百分之几」，应为完赛时间 |
| task_86 | 第三轮已修好。上轮把 track number 解成 `circuitId < 20`，漏 3 场 |

这些会随模型波动，有的轮次对、有的轮次错。提示词 18、20 条在管「名次列、阈值、分母」，**不能当已经修好**。

**修法：**

1. 题目里每个条件（时间、阈值、实体、名次列）在交卷前列成清单，代码里逐条过滤，并打印过滤前后行数。  
2. rank / position / positionOrder 以 `knowledge.md` 为准，不要猜。  
3. 「快百分之几」优先用时间，不要用速度，除非知识写明用速度。  
4. 同一题多轮对错不一致，优先加重跑和自检，而不是继续堆特例提示。

## 11. 已落地：交卷前列裁剪 + 全表扫描

针对 8.5（不完全匹配：列对了但多交了）和 8.2 / `task_22`（把预览当全表）。  
**不改题目、不写死字段。** 卡住的是交卷这一步：列太多就剪，行来自预览就退回重扫。

### 11.1 不完全匹配：按题目裁列

**解决什么问题**

评分按列内容签名匹配，**多交一列要扣分**（`0.1 × 多余列 / 交的列数`）。  
`task_38`：`trans_id` 全对，顺手交了 `date, amount` → 0.933。  
`task_379`：元素集合对了，把 `count` 也交了 → 0.95。  
提示词第 14 条写过「只交题目要的列」，模型仍把调试宽表直接交上去。

**怎么做**

调用 `answer` 且通过扫描检查后，再问模型一次（只根据题目 + 待交列名）：题目到底要哪些列。然后：

```text
待交列 ∩ 题目推断列
  有交集 → 只保留交集（行跟着切）
  交集为空 → 整表原样提交（列名猜飞时不要剪没）
  推断失败 → 同样原样提交
```

比较列名时忽略大小写，顺序跟待交表。

例子：待交 `trans_id, date, amount`，题目推断 `trans_id` → 只交 `trans_id`。  
待交 `element, count`，推断 `element` → 去掉 `count`。  
推断成 `withdrawals`、待交里没有这个名字 → 交集空，不剪。

trace 里 `answer` 的观察会带 `column_check`：`proposed` / `inferred` / `kept` / `dropped`。

**改了哪些文件**

| 文件 | 改动 |
| --- | --- |
| `src/data_agent_baseline/agents/answer_check.py` | **新建。** `infer_question_columns`、`intersect_columns`、`prune_answer_columns` |
| `src/data_agent_baseline/agents/react.py` | `_execute_checked_action`：真正交卷前调用 `prune_answer_columns`，裁完的表才写入 `prediction.csv` |
| `src/data_agent_baseline/agents/prompt.py` | 第 22 条：交卷时只留题目要的列，多余列会被交集裁掉 |

### 11.2 task_22：答案必须来自全表扫描

**解决什么问题**

`read_csv` 是**预览**：默认/示例 `max_rows=20`，模型还可能填 5/10/25。工具先读完文件再切前 N 行给你看，同时返回 `row_count`。  
`task_22` 问 Connor Hilton 哪天交会费。gold 两行：`2019-10-02`、`2019-09-12`。第二条在 csv 第 36 行，预览看不见。模型看到 `row_count: 36` 仍当全表，只交 10-02 → 整列 0 分。  
把 `max_rows` 调大治不了根，大表照样截断。该过滤全表时必须 `execute_python`（`csv.DictReader` / `json.load`，不要按预览行数截）。

**怎么做**

交 `answer` 时先检查轨迹，不通过则**拒收**（题目不结束，观察里写明原因，让它去跑 `execute_python`）：

1. 用过 `read_csv` / `read_json` / `read_doc`，但没有一次成功的 `execute_python` → 拒收。  
2. 从未成功跑过 `execute_python` 或 `execute_context_sql` → 同样拒收（连库都没查就交）。  
3. sqlite 可用 `execute_context_sql` 当全量查询；**只要碰过 CSV/JSON 预览，仍必须先 `execute_python`。**

`read_csv` 观察补了 `truncated`、`shown_rows` 和 `PREVIEW ONLY` 说明（截断时会写 `Showing 20 of 36 rows`）。

**改了哪些文件**

| 文件 | 改动 |
| --- | --- |
| `src/data_agent_baseline/agents/answer_check.py` | `used_preview_without_python`、`has_full_table_scan`、拒收时的 error/hint |
| `src/data_agent_baseline/agents/react.py` | `_execute_checked_action`：上述检查失败则 `ok=False`、不结束题目 |
| `src/data_agent_baseline/agents/prompt.py` | 第 21 条 + 任务提示：禁止用预览行交卷 |
| `src/data_agent_baseline/tools/filesystem.py` | `read_csv` 返回 `truncated` / `shown_rows` / `note` |
| `src/data_agent_baseline/tools/registry.py` | `read_csv`、`execute_python` 的工具说明改成「预览 vs 全表」 |

### 11.3 这两步不解决什么

口径选错（25 / 163 / 169）、并列被四舍五入拆掉（80）、空表策略（173）、超时（344 等）都还在。列裁剪只砍多余列，不会把算错的数改对；全表扫描只保证**看见了全部行**，过滤条件仍可能写错。

## 12. 语义层试错复盘（2026-09-24）

背景：在 dual-grain（细/粗两种聚合都探一遍）和保守列裁剪之后，50 题均分到过 **0.716**（run `20260924T025844Z`）。  
失败题里常见几类：grain 选错、字段映射错、过滤精度（时间字面量）、文档抽取。于是想加一层「语义假设」帮模型先定口径。

**结果：加了之后分数掉下去；改软、去硬规则也不够；最后整层拆掉。** 本节把试错写清楚，避免以后再走同一条路。

### 12.1 分数怎么掉的

| run | 大致配置 | mean_score | 相对峰 |
| --- | --- | ---: | ---: |
| **`20260924T025844Z`** | dual-grain + 保守 prune（**峰**） | **0.716** | — |
| `20260924T050141Z` | 硬 semantic contract（假设当约束） | 0.564 | −0.15 |
| `20260924T063455Z` | 软 hypothesis + hard rule + 拒答门 | 0.586 | −0.13 |
| （之后） | 去掉 hard rule → 再去掉冲突文案 → **完全删除语义层** | 待复跑 | 目标回到峰附近 |

峰之后两轮都在往下拉。软一层比硬一层略好，但仍然远低于不加语义层时。

### 12.2 我们试过什么

按时间顺序：

1. **硬 binding contract**  
   LLM 先写一份 JSON「合同」（grain、列、行数、禁止项），注入提示词，交卷时按合同检查。  
   想法：锁住口径，少猜。  
   实际：合同猜错就整题锁死；25 / 27 / 80 等被带偏，均分掉到 0.564。

2. **软 hypothesis + hard rule + 证据门**  
   合同改成「软建议」；再用正则 hard rule 打补丁（例如题里有 full name 就禁止 merge；极值强制 row + all_ties）；probe 后再拒答。  
   想法：软引导、硬兜底、有证据才拦。  
   实际：硬规则和拒答门误伤正确交卷，均分 0.586。

3. **只去掉 hard rule**  
   不再用正则改假设。  
   实际：拒答门和「假设 vs knowledge」两套声音还在，根因没消。

4. **去掉冲突文案 / 关掉注入与拒答**  
   任务消息只留 Question + knowledge；拒答恒为通过。  

5. **完全删除语义层**（当前）  
   删掉 `semantic_layer.py`；knowledge 检索挪到 `prompt.py`；trace 不再带 `semantic_contract`。  
   保留：Question、knowledge snippets、ReAct、dual-grain、列裁剪、全表扫描检查。

### 12.3 为什么会伤分（说人话）

语义层本意是「帮模型少犯错」。落地后变成**第二套题意**，和本题真正权威的东西抢话：

| 权威应该是谁 | 语义层实际干了什么 |
| --- | --- |
| 题目原文 `Question` | 又写一个 `ask` 改写，模型当第二题干 |
| `knowledge.md` 公式 / 编码 | `knowledge_hooks`、`grain`、`measure` 常是模型猜的，还排在 knowledge 前面 |
| 库里真实 probe | 拒答门用「全程 probe 最大行数」当「答案该有几行」 |

三处典型误杀（`063455Z` 可复核）：

**（1）`full_name` 过滤器被当成「禁止合并姓名」**  
`task_74`：题是「full name 是 Karen … 的英雄眼睛颜色」。SQL 用 `WHERE full_name = ...` 完全正确。  
hard rule 见题里有 “full name” 就加 `forbidden: merge_full_name`；拒答门见 SQL 里出现 `full_name` 就拒。  
正确答案反复被拒，步数用尽 → 峰分 1.0 → 缺交 0。

**（2）探查 10 行 ≠ 答案该有 10 行**  
拒答用 `_max_probe_rows`：把对话里**所有**成功 SQL 的 `row_count` 取最大值。  
中间 `LIMIT 10` 宽表一旦 10 行，最终答案只有 1 行就被判「折叠多匹配」。  
`task_218`：电话对了，被拒到超时。  
`task_292`：本该只交最高分车队的一个 url；被拒后改交 race 9 全部 10 个 url → 0 分。

**（3）极值 hard rule 推错 grain**  
`task_25`：「哪个活动成本最低」。峰分时内容对（多交一列小扣）。  
软层强制偏好 row + dual-grain 推到 `SUM(spent)=0` 的一堆活动；gold 是 cost=6 的三个 Speaker → 0 分。

另外：`ground_sql` 常 invent 不存在的表；失败后 `ambiguous` 仍塞进提示，增加噪音。

### 12.4 和 knowledge 的冲突点（设计层面）

任务消息里一度同时出现：

1. Question（权威）  
2. soft hypothesis（自称 soft，但带 forbidden，且拒答真拦）  
3. knowledge snippets（系统又说 knowledge 权威）  
4. system 里 dual-grain / full name 拆分等规则  

模型不知道听谁的。文案写「probe 优先」，却**没写 knowledge 优先于 hypothesis**；18b 还写「Obey hard forbidden」—— soft 名、hard 实。

**结论：** 在这套赛题上，额外「语义合同 / 假设」和已有 knowledge + ReAct 提示是**同级竞争者**，不是安全的上层。分数上已经证明：峰分来自 dual-grain + 保守 prune，不来自语义层。

### 12.5 留下的经验（可当纪律）

1. **先定点修错题，少加全局框架。** 框架一宽，正确题也被误伤；均分容易掉。  
2. **拒答门的证据必须极严。** 禁止用「任意中间 probe 的行数」当答案基数；禁止用「题干出现某词」去禁 SQL 里同名列（过滤 ≠ 输出合并）。  
3. **knowledge 与 Question 之上不要再塞第二题意。** 需要旁注也只能极短，且明确：knowledge > 旁注；冲突时忽略旁注。  
4. **「软」若配硬拒答，就不是软。** 要么只注入不拦截，要么别注入。  
5. **回滚要快。** 峰分 run（`025844Z`）应当作基线；新方案先比峰，掉了就撤，不要在掉分方案上连改两轮「软化」。  
6. **当前代码立场：** 无语义层；只保留 knowledge 片段检索 + 既有交卷守卫。抬分继续对着峰分仍错的题做**单题定点**（提示 / 工具行为），不新开口径框架。

### 12.6 当前代码落点（删除后）

| 曾有 | 现在 |
| --- | --- |
| `agents/semantic_layer.py` | **已删** |
| 假设 draft / ground / 拒答 | **无** |
| knowledge 检索 | `agents/prompt.py` 里 `retrieve_knowledge_snippets` |
| 任务消息 | Question → 仓库说明 → knowledge snippets |
| 仍保留 | dual-grain 检查、列裁剪、全表扫描、ReAct |

复跑时对比 `20260924T025844Z`：若接近 0.716，说明拆层方向对；若仍低，查的是 dual-grain / 提示 / 模型波动，不是语义层残留。

## 13. 先验学习与冠军对照（2026-09-24）

第 12 节拆掉语义层之后，又讨论过三条「先把知识学细再解题」的路，以及冠军提交版实际在做什么。结论先写在这里：**不要另写一份先验。解题只拿题目原文、knowledge 原文、对表查到的数。** 冠军交卷的入口也是这条，没有 pre，没有 plan。

### 13.1 又否掉的三条

| 方案 | 当时的想法 | 为什么不行 |
| --- | --- | --- |
| 多轮 Draft / Refine | 把题目或口径改几稿再答 | 改稿会离开 knowledge 里的真实案例，上下文和原文各说各的 |
| 对 knowledge 里的 case 多轮学习，概念由粗到细 | 先学案例，再拆步骤、探测修复、多轮验证 | 没有外部对错标准时，「细化」就是模型自己写一条新规则。`task_11` 把「ID 必须相等」收成「差几以内算同一人」。示例 SQL、公式经常本身就缺列或和题目不一致，多读几轮只会把错示例记牢。学习轮还吃步数，Hard 题更容易空卷 |
| 先验只摘 use case 里的指标原句，用来减少幻觉 | 先验不发明规则，只把指标含义写清楚 | 模型很少整段照抄，会把 `Thrombosis = 2` 收成「重度是较高的编码」。use case 对不上本题时，摘得越清楚，模型越敢照错公式做。能压住的只是「原句在、模型看漏了」；漏行、滤成空表、超时补不上 |

冠军仓库里的 `pre_agent.py` 几乎就是第三条：SQL 形态对得上才摘原文，对不上留空。`zz_agent_v2.py` 里调用和注入都注释掉了。`plan_agent.py` 会先查数再写一份 markdown 规划，主流程没有 import，也没有调用。

### 13.2 冠军提交版实际在做什么

入口是 `kddcup2026_champion-main/src/data_agent_baseline/zz_agent_v2.py`。真正交卷的只有 solver。

1. **knowledge 全文**放进 solver 指令，不检索、不改写、不学习。
2. **表描述不是一段说明，就是 schema。** `describe_tool` 读 csv / json / sqlite，写出表名、列名、类型、行数、两行样例。没有「这张表是患者花名册」这种句子。
3. **表相关判断只折叠描述。** 模型对照题目、knowledge、视频口径和每张表的列清单，投票这张表解这题是否必须用到。判无关时，提示里的列和样例换成一行「已折叠」。表仍在 `explore_data` 里，可以直接查。判失败或拿不准，默认当相关。文档抽出的表不参加这次判断。
4. **对表查 SQL** 是工具 `explore_data`：只读 `SELECT`，核对行数、取值、精确 join 命中几行。默认最多回 50 行，同时告诉总行数。查通的 SQL 再写进脚本。
5. **`solver.py` 是每题生成的交卷脚本。** 路径、读表、`run_sql`、保存 `prediction.csv` 已经写好，中间是 `result = None`。agent 只改这一句查询。不改的话脚本能跑，但没有结果表。失败重试时先恢复成空白脚手架再重写。最多约 80 轮，失败最多 5 次。

pre / plan 的设计（摘 case、写规划）留在仓库里，**没有进提交结果**。

### 13.3 照这个结论改了 PHASE_1

不接 pre，不接 plan，不写先验。改的是现在的 ReAct。

1. **上下文一次装好。** knowledge 放得下就整篇进提示（上限约 16000 字）。更长时按词面保留整节和标题，不在半节截断，不改写。表 schema（表名、列、类型、行数、两行样例）由程序生成后放进任务消息。
2. **先查再交。** 最终 SQL 前要查编码列的实际取值、精确 join 命中行数、极值命中行数。这些数留在观察里。
3. **交卷看行数。** 最终结果 0 行则拒收，观察里附上 SQL 提到的列的最小值、最大值和行数。极值查询若带尾部 `LIMIT`，且去掉 `LIMIT` 后行数更多，拒收，要求等值条件交出全部并列。题目写明 top N 且 `LIMIT` 等于 N 时不拦。
4. **没交表单路再跑一次。** 批量时先不在并发池里重试；本批结束后，没有 `prediction.csv` 的题单独再跑一次。配置 `run.empty_retries`，默认 1。同题若交出多张表，按列签名取得票最多的那一张，不把各次的行并起来。

**改了哪些文件**

| 文件 | 改动 |
| --- | --- |
| `agents/prompt.py` | 短文整篇注入；长文整节保留。任务消息改为 knowledge 原文，不再称 snippets |
| `tools/warehouse.py` | `format_table_schema`：程序生成表描述 |
| `agents/react.py` | 开跑前装入 knowledge 和 schema；交卷前走行数门禁 |
| `agents/submit_rows.py` | **新建。** 零行拒收、极值 `LIMIT` 藏并列则拒收 |
| `run/runner.py` | 空卷在并发之外再跑一次；`select_majority_answer` 取得票最多的表 |
| `config.py` | `run.empty_retries`，默认 1 |

单测：`_test_knowledge.py`（整节不改写）、`_test_submit_rows.py`（零行、并列、投票不并行）。**50 题还没按这版复跑**，不能当成已经抬分。对照仍是峰分 run `20260924T025844Z`（0.716）。第 12.6 节里的「knowledge snippets」是拆语义层当时的代码，以本节为准。
